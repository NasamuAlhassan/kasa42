01

What the task actually was

Ghana NLP granted a 48-hour window on a shared NVIDIA H200 and pointed at ghananlpcommunity/ghana-speech — 42 language subsets, 2,334.9 hours, 1.41 million segments, pre-staged on the box at /data/ghana-speech. The brief was open: build something.

The starting point was DONDO (KhayaAI/w2v-bert-…, Apache-2.0), which covers 11 Northern Ghanaian languages at around 10.3% WER. Three things were added to it:

  • 11 → 42 languages in a single checkpoint.
  • Language identification. DONDO conditions on a one-hot language prefix, so the caller has to already know what is being spoken — circular for most real uses. A jointly trained head removes that.
  • A book-disjoint benchmark, and an actual test of whether book-disjointness matters.

The third item is the one that turned out to be most interesting, and not in the direction expected.

02

Why these choices

w2v-BERT 2.0 over Whisper

Segments in this corpus have a median duration of 4.9 seconds. Whisper pads every input to 30 seconds, so roughly 80% of its compute would have gone into zeros. w2v-BERT is a plain encoder over variable-length audio, is 10–30× faster to fine-tune at comparable WER, and beats Whisper outright on genuinely low-resource languages — which describes 30 of the 42 here.

DONDO over raw facebook/w2v-bert-2.0

DONDO has already seen this language family and this recording domain. With a 48-hour budget, starting from a checkpoint that knows Kusaal is worth more than architectural purity. The cost is a caveat that has to be carried: DONDO's own training books are unpublished, so a small unquantified overlap with any test set is possible.

Extending the vocabulary, not replacing it

DONDO ships 49 tokens; 42 languages need more. Rather than renumbering, every shared character keeps its original index, so extend_ctc_head can copy DONDO's trained output rows straight across. 49 rows transferred, 47 new characters initialised fresh, 96 total.

The consequence people get wrong

The CTC blank is [PAD] at index 33, not 0, because that is where DONDO put it. Every decode path takes blank_id explicitly. Any code that assumes blank is 0 silently produces garbage rather than failing.

Folding homoglyphs

DONDO's published vocabulary contains both U+0511 ԑ and U+025B ɛ, and both U+2184 ↄ and U+0254 ɔ — the same letter competing for probability mass across two of only 49 output units. Real corpora contain both because typists reach for whatever the keyboard offers. Folding costs nothing and removes the split.

Splitting by book

source_file parses as BOOK.CHAPTER.VERSION, so the corpus is Bible audio. A random segment split puts adjacent verses — same narrator, same session, minutes apart — on both sides of the boundary. Splitting by book avoids that.

There is a trap immediately next to it. Splitting on (version, book) looks more careful and is worse: it puts Genesis-v1 in train and Genesis-v2 in test — different audio, byte-identical transcript. Six languages contain the same book under multiple versions, so this is not hypothetical.

03

The pipeline

Six stages, each consuming the previous one's output. Everything before training reads only metadata columns via parquet projection, so all 42 languages could be audited without touching the audio.

StageProducesScale
build_manifestmanifest.parquet1,411,467 rows · 44 MB · ~1 min
splitssplits.json1,801 books, 26–66 per language
vocabvocab.json96 tokens · 97.3% of text trainable
mixturemixture.json700 h from 2,030 h · 393,160 segments
testsettwo evaluation sets8,400 + 7,540 utterances
trainfinal.pt24,000 steps · ~6 h

The manifest was network-bound and hours long until the data turned out to be already on the box; --local-root made it disk-bound and about a minute.

The mixture

Raw, the corpus is ~16× imbalanced — Asante Twi has 200 hours, Mampruli about 25. Training on that produces a model excellent at Twi and useless on the tail, which defeats covering 42 languages at all. Temperature sampling at α=0.5 with a 40 h per-language cap takes the largest language's share from 8.5% to 4.9%, and 2,030 available hours down to 700 — which is the single reason the run fits in hours rather than days.

Read these to the nearest few points

Three independent draws of the same test design gave micro WER of 30.3%, 30.0% and 30.2% — but individual languages moved by up to 7.3 points (Ninkare 57.2% → 64.5%). At 200 utterances per language the micro-average is stable to a few tenths and the per-language figures are not. Quoting them to one decimal would be misleading.

Language identification is the strongest result

96.8% mean accuracy over 42 classes, where chance is 2.4%. Four languages hit 100%, the floor is 91.5%. This is the capability DONDO explicitly does not have, and it is what makes a single microphone button possible instead of a language picker.

Against other systems

Each row recomputes both sides over only the languages that system covers. Comparing an average over 34 covered languages against an average over all 42 would flatter whichever system declined the hardest ones.

Whisper large-v342102.3%30.2%57.3%10.5%
MMS-1B-all3425.7%29.2%12.1%9.7%
DONDO (unconditioned)875.9%27.6%40.8%14.1%

MMS-1B-all beats us on WER by 3.5 points. We beat it on CER by 2.4, cover eight languages it has no adapter for, do language identification it does not do, at roughly 60% of its parameter count.

The WER/CER split is the informative part. MMS's ratio is 2.1×, ours 3.0× — we get more characters right and more words wrong. That is a word segmentation weakness, not an acoustic one, and the same signature appears per-language (Bissa: 40.9% WER against 9.5% CER). Space prediction is the obvious next thing to work on.

The DONDO row is not a fair comparison

DONDO conditions on a one-hot language prefix. Our harness supplies none and runs it as a plain CTC model, so 75.9% is a lower bound on its ability against a published ~10.3%. The README originally claimed the prefix was supplied; it never was. The number is reported for transparency about what was run, not as evidence about DONDO.

05

The leakage experiment, and its negative result

The project's stated thesis was that a random split flatters WER, and that the gap between a leaked and an honest split is the point. It was tested properly. The gap is not there.

Identical weights were scored on two sets: segments from held-out books, and segments from seen books that the model was never trained on. Both contain only unseen utterances; the sole difference is whether the book was seen.

Constructionhonest − leaked95% CI
Unmatched−1.1pp[−1.9, −0.3]
Book-diversity matched−0.7pp[−1.4, +0.1]

The matched interval spans zero. On these weights, book-level overlap confers no measurable advantage.

The first attempt was confounded, and measuring it showed how

The first construction gave −1.1pp with an interval excluding zero — the book-disjoint split appeared reliably easier, which is backwards. Inspecting the two sets explained it:

SetBooks / configWords / uttDuration
honest4.220.257.85 s
leaked27.219.317.62 s

Six and a half times the content diversity, and 4.9% shorter references. Both make the leaked side harder for reasons that have nothing to do with leakage — in exactly the direction observed. The comparison varied two things at once. --match-books restricts the leaked draw to as many train books as the config has test books, leaving book-seen-ness as the only difference.

What can honestly be claimed

That the model is not memorising books at this scale — one pass over 700 hours, at 30% WER — not that leakage cannot occur. A longer-trained or higher-capacity model may behave differently. And chapter-adjacent leakage, the strongest form, was not tested: a naive split puts consecutive verses from one recording session on both sides, and our leaked set samples across whole books, which dilutes that.

Book-disjoint splitting remains the conservative default. This result says it cost nothing.

06

Does it know the language, or one studio?

Every number so far comes from one corpus. A model trained and tested on a single recording project cannot distinguish having learned a language from having learned a studio. So it was scored on an independent Kusaal corpus — 81.7 hours from Faith Comes By Hearing, Davar and Global Recordings Network, force-aligned into 9.5-second clips against GILLBT text.

Restricted to the 11 books KASA-42 held out of training. That restriction is not fussiness: the corpus ships its own test split, and all four of its held-out books — plus all four validation books — are in KASA-42's training books. Scripture corpora share a translation, so scoring there would have measured sentences the model had already seen, with only the audio new.

Test setClipsWERCERLID
ghana-speech (version 3752)20030.2%16.3%95.5%
Independent corpus (FCBH / Davar / GRN)2,89537.9%21.9%99.8%

Transcription degrades about 25% relative on unfamiliar recordings of the same language and domain. That is the honest cost of changing recording source, and it is the number to quote when asked what this model would do on audio from anywhere else.

Language identification goes the other way — up to 99.8% across 2,895 clips from a different ministry, a different alignment pipeline and different narrators. The LID head keys on the language and not the channel. That is the claim the language-ID contribution rests on, and it was previously untested.

07

Three things the corpus was hiding

id is not a unique key

In 13 of 42 configs, by factors up to 1.52× — Sisaala has 47,096 rows against 31,074 distinct ids. Anything selecting segments by id, which is the obvious design, silently over-samples those languages.

What makes it hard to catch is that the accounting reconciles either way. Hours are summed over rows, so the printed totals are correct under both readings and nothing looks wrong. Sisaala's 22.9-hour allocation would have trained on roughly 34.8 hours, making a tail language joint-largest in the mixture above Ewe and Hausa — precisely the imbalance the mixture exists to remove. It surfaced only because a test set had an exact cap to check against: --max-per-config 200 returned 380.

One version code, two narrators

Kusaal is 100% version 3752, and the Phase 0 audit concluded from that it was a single recording project and therefore one narrator. ECAPA-TDNN speaker embeddings over one clip per book, clustered against a threshold calibrated from same-book pairs, split it cleanly:

ClusterBooksHoursContent
12839.7100% Old Testament
2, 0, 412~6100% New Testament

A perfect OT/NT split with zero crossover — the two testaments were recorded as separate campaigns, as they usually are. Fine-tuning single-speaker TTS across that boundary averages two voices into a muddy one, and the metadata gives no warning at all.

Hebrew in Ewe and Hausa

21 characters — א ב ג ד ה ו ז ח ט י כ ל מ נ ס ע פ צ ק ר ש ת — appearing 67 times across 1.41 million segments. Not an encoding fault: Psalm 119's acrostic stanza headings, one per Hebrew letter, which is exactly the count you would expect.

And three figures that were simply wrong

QuantityPhase 0 estimateActual
Corpus hours2,2472,334.9
Kusaal hours81.672.5
Books per language9–5226–66

Hours had been inferred from audio bytes at 32,000 B/s and validated against the dataset card: Asante Twi, 23.06 GB / 32000 = 200.2 h against a stated 200.02. Flawless — and misleading, because Asante Twi is the largest config, where WAV container overhead disappears into the rounding. On Kusaal the same method ran 13% high.

The general lesson

A byte-derived estimate validated on your biggest partition is validated where the error is smallest. Check the smallest one too.

08

The bugs

Eleven of consequence. They are listed because most of them would have produced numbers that looked entirely reasonable and were wrong — which is the failure mode that matters in a project whose contribution is measurement.

Boolean flags that silently did nothing

Invisible
Cause
from __future__ import annotations makes f.type the string "bool", so f.type is bool never matched. Every boolean became a value-taking option.
Effect
--gradient-checkpointing demanded an argument it should not have, and --transfer-head False parsed as bool("False") — which is True.
Found
By reading --help while verifying something else. It had been latent since the file was written.
Fix
Test the default, not the annotation.
if isinstance(f.default, bool):
    if f.default:
        # Defaults on, so the useful flag is the one that turns it off.
        # A store_true here would flip the default to False and quietly
        # disable the DONDO head transfer.
        ap.add_argument(f"--no-{name}", dest=f.name,
                        action="store_false", default=True)
    else:
        ap.add_argument(flag, action="store_true", default=False)

Duplicate ids skewing the mixture and the WER

Would have shipped
Cause
id repeats in 13 configs. Both the mixture pool and the loader selected by id, so every copy came along.
Effect
Affected languages trained on up to 1.52× their allocation, and their utterances were double-weighted in per-language WER — in the one table the project exists to publish.
Fix
Key on id at both ends, and have both pick the same copy — the shortest, since manifest row order is thread completion order and not stable across rebuilds.

A 33-point gap printed as “+0.3pp”

The headline
Cause
WERs are fractions; the inflation column formatted the gap with .1f and labelled it pp.
Effect
The leaked-vs-honest table — the entire point of the project — would have understated its own result by 100×.
Found
Testing the report function on synthetic scores before any real ones existed.
-  lines.append(f"{k:24s} {l:>8.1%} {h:>8.1%} {h - l:>+10.1f}pp")
+  lines.append(f"{k:24s} {l:>8.1%} {h:>8.1%} {(h - l) * 100:>+9.1f}pp")

Two RNG streams that were secretly one

Looked like a finding
Cause
A single generator shuffled the honest then the leaked selection for each config in turn. A shorter leaked list consumed a different number of draws, so every later config's honest sample started from a different state.
Effect
--match-books, which must not touch the honest set, moved honest Ninkare by 7.3 points. It looked exactly like a real effect.
Fix
A stream per (seed, config, side).
Silver lining
The accident measured the sampling variance at n=200 directly — which is why the per-language table is now quoted coarsely.

Evaluation OOM at utterance 8,000 of 8,400

A full pass
Cause
Sorting by duration ascending, then taking fixed groups of 16. The final batches were therefore all 29-second clips: 469 seconds of audio in one forward pass, against the 120 the rest of the stack budgets for.
Effect
It failed at the end of the job, having done all the work — the most expensive possible place to fail — and only once a neighbouring tenant grew.
Fix
Budget padded duration, not count, so the last batch costs what the first one costs.
for i in order:
    d = float(durations[i] or 0.0)
    if cur and (max(longest, d) * (len(cur) + 1) > batch_duration
                or len(cur) >= batch_size):
        batches.append(cur); cur, longest = [i], d
    else:
        cur.append(i); longest = max(longest, d)

A 309 MB parquet row group

Public and broken
Cause
PyArrow defaults to about a million rows per row group. For audio at ~300 KB a clip, each 400 MB shard became one 309 MB group.
Effect
A reader must decompress an entire row group to return any row in it, so showing five rows meant scanning the whole shard. The Hub's viewer refused the dataset outright.
Fix
Size row groups from the audio actually present, and write a page index.

An unfair number about someone else's model

Reputational
Cause
run_dondo filtered to DONDO's languages and then ran it as a plain CTC model. It supplied no language prefix, despite the README claiming it did.
Effect
DONDO scored 75.9% against a published ~10.3%. Publishing that as a comparison would have been the one genuinely unfair claim in an otherwise careful project.
Fix
Withdrawn as a comparison in three places — README, model card, and a warning printed by the script that produces it.

datasets 5.x demanding torchcodec

~1 h
Cause
The Audio feature began decoding through torchcodec on every row fetch.
Effect
A DataLoader worker died on the first batch, before a single step.
Fix
Not installing torchcodec — nothing here wanted a decoded array. decode=False leaves the column as {bytes, path}, which the existing soundfile path already accepted.
def undecoded_audio(ds):
    import datasets
    if "audio" not in ds.column_names:
        return ds
    return ds.cast_column("audio", datasets.Audio(decode=False))

A neighbour who grew from 42 GB to 100 GB

~3 h of steps
Cause
The H200 was shared. Another tenant's footprint moved by 60 GB inside one evening, invisible except as No running processes found beside 100 GB of usage.
Effect
Training died at step 300 while using only 38.9 GB itself.
Fix
Gradient checkpointing to ~15 GB, and an OOM-skip: drop the batch, empty the cache, continue. Eight consecutive means the room is genuinely gone, so it saves a resumable checkpoint and exits saying what to resume with.

10,000 files per directory

A silent, unusable dataset
Cause
A Hub repo is git-backed. A 24,597-clip train/ directory was rejected mid-push.
Effect
Worse than a clean failure: 11,597 rows landed, the subdirectories were read as class labels, and the dataset appeared publicly as audio classification with a null label column and no transcripts at all.
Fix
Parquet shards with the huggingface schema metadata written directly, so packing needs no torchcodec either.

A requirements.txt that replaced torch

The last hour
Cause
pip install -r on a third-party trainer's requirements, into the shared conda environment everything else depended on.
Effect
torch 2.5.1+cu124 → 2.13.0+cu130, and CUDA stopped working because the driver predated cu130. It surfaced as transformers being unable to import Wav2Vec2BertModel.
Fix
Force-reinstall the matching pair. The real fix was --no-deps, or a separate virtualenv, twenty minutes earlier.

The pattern worth extracting

Four of these are the same shape: a library default that is correct for text and wrong for audio. A fixed batch count. A million-row parquet group. An Audio feature that decodes eagerly. A directory of files. None of them error at small scale; all of them fail at full size, and two of them failed at the very end of a long job.

Watching a run that will not speak

| tee hands Python a pipe, so stdout block-buffers at 8 KB — roughly 2,350 steps, the better part of an hour, before a line appears. Restarting with python -u would have cost every step so far. Checkpoint timestamps give a measured rate instead, and unlike elapsed-time arithmetic they exclude dataset loading: 

if len(pts) >= 2:
    (s0, t0, _), (s1, t1, _) = pts[0], pts[-1]
    if t1 > t0:
        rate = (s1 - s0) / (t1 - t0)
        return rate, s1 + rate * (now - t1)
10

What this is not

  • Not the first Kusaal speech model. facebook/mms-tts-kus exists, MMS-1B-all covers Kusaal ASR, and DONDO covers Kusaal at 13.3% WER.
  • Not the most accurate model here. MMS-1B-all is 3.5 points better on WER over the 34 languages it covers.
  • Not tested on conversational speech. Everything is read scripture — formal, archaic, proper-noun dense, studio-recorded. The cross-corpus result measures robustness to recording conditions, not to spontaneous speech, which remains untested.
  • Not a fair measurement of DONDO. See above.
  • Not commercially usable. CC BY-NC 4.0, inherited from the training data. DONDO is Apache-2.0, so this is a licensing downgrade for anyone who could have deployed DONDO.

What is left after all that: broader coverage in one checkpoint, language identification DONDO does not have, results on a split that does not leak, and the leakage question actually tested rather than asserted.

Reproducing it

Everything below runs from the public repository and public data. On a machine with the corpus staged locally, Phase 0 takes minutes. 

git clone https://github.com/NasamuAlhassan/kasa42 && cd kasa42
pip install -e '.[train,serve]'

python -m kasa42.doctor --data-dir /data/ghana-speech

python -m kasa42.data.build_manifest --local-root /data/ghana-speech --workers 16
python -m kasa42.data.splits
python -m kasa42.data.vocab
python -m kasa42.data.mixture --alpha 0.5 --cap-hours 40
python -m kasa42.asr.testset --data-dir /data/ghana-speech --match-books

python -u -m kasa42.asr.train --max-steps 24000 --batch-duration 160 \
  --gradient-checkpointing --data-dir /data/ghana-speech

python -u -m kasa42.pipeline --repo <you>/kasa42-asr

doctor first is not ceremony: it checks free VRAM across all tenants, whether bf16 is hardware or emulated, that HF_HOME points somewhere with room, and that all four training artefacts exist — and exits non-zero if not.

If you take one thing from the code

Keep vocab.json. It maps CTC indices to characters, and the blank is [PAD]=33 rather than 0. Without it the published weights cannot be decoded by anyone, including the person who trained them.

12

What I would do differently

  • Check the smallest partition, not the largest. The byte-derived duration estimate validated perfectly on the biggest config and was 13% wrong on a small one.
  • Never assume a key is a key. One len(set(ids)) == len(ids) at manifest time would have caught the duplicate-id problem on day one instead of day two.
  • Install third-party requirements into a separate environment. One pip install -r cost the last hour of the window and a trained model with it.
  • Budget audio work in seconds, not items. Every count-based default — batches, row groups, files per directory — broke at full size.
  • Upload the small files first. A 2.42 GB checkpoint went to the Hub; the 7 KB vocabulary it needs nearly did not.
  • Test the report before the result. The +0.3pp formatting bug was in the one table the project was built to produce.
